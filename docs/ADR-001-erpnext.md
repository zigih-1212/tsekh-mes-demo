# ADR-001. ERPNext как основа системы автоматизации производства: использовать / доработать / заменить

**Контекст.** В вакансии требуется объединить планирование → производство → склад ГП в одной системе
«на базе ERPNext» и оценить, что в ERPNext использовать, что доработать, а что заменить своим кодом.
Этот документ — инженерная оценка; демо-реализация (этот репозиторий) показывает свой контур MES поверх
той же доменной модели.

## Что берём из ERPNext как есть (использовать)

1. **Номенклатура и единицы учёта** — Item, UOM, складская аналитика.
2. **BOM (Bill of Materials)** — многоуровневые спецификации, у нас пока один уровень (материалы → изделие),
   в ERPNext уже есть — используем его.
3. **Складской учёт (Stock Ledger)** — приход/расход/списание, это ровно наш `StockMove`; в ERPNext — Stock Entry.
4. **Пользователи и роли** — встроенная RBAC-модель (Role Permission Manager) покрывает admin/director/storekeeper.
5. **Производственные заказы (Work Order)** — планирование, статусы, списание материалов по BOM — используем,
   но статусную модель расширяем под наш жизненный цикл.
6. **Отчёты и дашборды** — Report Builder / Query Report для руководства.

## Что дорабатываем (кастомизация, Frappe-app поверх ERPNext)

1. **Маршрутные операции (routing) со сдельной оплатой.** В ERPNext Work Order есть операции (Operation),
   но расчёт сдельной оплаты по операции с фиксацией ставки на момент выпуска — дописываем своим DocType
   (`Work Task` с полями qty_done/qty_rejected/rate snapshot), триггером на Work Order.
2. **Статусы заказа под наш процесс:** planned → released → in_progress → completed / cancelled,
   с проверкой остатков и автосозданием заданий при release (в ERPNext делаем через server script / контроллер).
3. **Приёмка ГП частями** с автозавершением заказа — Manufacturing Receipt + доп. валидация.
4. **Low-stock алерты** по порогу min_stock — в ERPNext есть Reorder Level, используем + уведомления.
5. **MES-экран оператора** (простое рабочее место: «мои задания → начать → годные/брак → завершить»)
   — отдельный лёгкий фронтенд (как в этом демо), ERPNext-UI для этого плохо подходит.

## Что заменяем своим кодом (и почему)

1. **Оперативный контур «выпуск → задания → приёмка»** — в демо это отдельный сервис (FastAPI + SQLite),
   потому что на производстве нужны **миллисекундные отклики, офлайн-устойчивость и простая схема**.
   В проде этот контур синхронизируется с ERPNext (или ERPNext остаётся системой учёта, а MES — системой
   сменного задания; выбирается на этапе пилота).
2. **Сдельный расчёт (payroll)** — считаем своим кодом: ставка фиксируется на момент выпуска заказа
   (иначе ретроспективно пересчитывать зарплату нельзя), в ERPNext этого нет из коробки.
3. **Жёсткая валидация брака** (годные + брак ≤ задание, причина брака обязательна) — свой код поверх.

## Почему не «всё в ERPNext одной кнопкой»

ERPNext силён в учёте и документах; производственный сменный контур (оператор у станка) требует другого UX
и других гарантий по скорости. Компромисс: ERPNext — учётная система (номенклатура, склад, бухгалтерия),
кастомный MES — операционный контур, обмен через API/события. Этот репозиторий — демо MES-контура.

## Что будет в проде (не в демо)

- PostgreSQL вместо SQLite, миграции Alembic (в демо — `create_all` для простоты старта).
- Docker Compose, CI (pytest + build фронта), мониторинг.
- Интеграция с 1С/бухгалтерией через API ERPNext.
